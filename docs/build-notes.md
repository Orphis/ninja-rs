`Cargo.toml` / `Cargo.lock` are the source of truth for crates; Bazel
consumes them through `rules_rs`' `crate.from_cargo` (hub `@crates`). The
lock file was generated with the local cargo 1.91, so it is MSRV-compatible
with 1.88+ (`rust-version`), which lets `cargo build/test` work as a
development convenience; the Bazel build uses Rust 1.99.

## Why rules_rs

hermetic-llvm's README recommends rules_rs for Rust/CC interop: it registers
Rust toolchains whose linker is the `@llvm` clang/lld-link, provides target
triple platforms, and resolves crates directly from `Cargo.lock`. Linux and
gnullvm builds work unpatched; the Windows MSVC build needs the patches below.

## Patches (Windows MSVC)

Upstream only exercises Rust on Windows through gnullvm; with an MSVC host
and target, four problems needed patches in `third_party/patches/`, applied
from `MODULE.bazel`. Each only changes behavior for MSVC targets or Windows
hosts, and each should go upstream:

| Patch | Module | Problem | Fix |
|---|---|---|---|
| `llvm-msvc-exec-overlay-cycle.patch` | `llvm` (`single_version_override`) | Every MSVC compile/link uses a case-insensitive SDK overlay generated by a tool built for the exec platform; with an MSVC exec platform the tool depends on itself (analysis-time cycle). | When Bazel runs on Windows (case-insensitive filesystems), the runtime stages (`stage0`, `stage1`, `stage1_hosted`, which build the tool) skip the overlays; user code (`complete`) keeps them. |
| `rules_rs-msvc-lld-link.patch` | `rules_rs` (`single_version_override`) | rules_rs gives rustc the cc toolchain's link tool, the clang-cl driver, but rustc passes link.exe-style arguments for MSVC targets. | MSVC Rust toolchains link with `@llvm//tools:lld-link` directly (`linker_preference = "rust"`). Not `rust-lld`: its path inside the generated sysroot exceeds `MAX_PATH`, which LLVM tools need to locate themselves. |
| `rules_rust-linker-preference-unset.patch` | rules_rust (`rules_rust.patch`) | `linker_preference` rejects `""`, so a `select()` can't leave it unset for non-MSVC triples. | Allow `""` (already treated as unset by the implementation). |
| `rules_rust-msvc-link-search-args.patch` | rules_rust | With a direct linker, rules_rust keeps only Unix search flags from the cc toolchain's link args; MSVC ones are dropped, so the SDK/CRT libraries are not found. | Keep `/LIBPATH:` and `/vfsoverlay:`, including clang-cl-forwarded `/clang:-Xlinker /clang:<option>` pairs. |
| `rules_rust-msvc-build-script-no-vs-probe.patch` | rules_rust | cc-rs (in build scripts) finds a locally installed Visual Studio through the registry and merges its `LIB`/`INCLUDE` into the hermetic clang-cl, leaking host paths (rejected by the build-script runner). | For MSVC targets, set `VCToolsVersion` to a version that cannot exist, which find-msvc-tools documents as restricting its search. |

rules_rust patches are one file each: Bazel's patcher misplaces hunks of
multi-file patches. The Windows platforms are named `win_msvc` (short): with
`--experimental_platform_in_output_dir` the name is in every output path, and
deep libc++ header paths otherwise exceed `MAX_PATH` in `@llvm` tools.

## Hosts

- **Linux x86_64** (verified in WSL Ubuntu 22.04): `bazelisk build
  --config=linux //...` and `bazelisk test --config=linux //...` (the
  `linux` config is applied automatically on Linux hosts through
  `--enable_platform_specific_config`). Toolchain resolution selects
  `@llvm//toolchain:linux_x86_64_cc_toolchain` and the rules_rs
  `default_linux_x86_64_1_99_0_rust_toolchain`; rustc links with
  `external/llvm++llvm_toolchain_minimal+llvm-toolchain-minimal-linux-amd64/bin/clang++`
  (checked with `--toolchain_resolution_debug` and `aquery`).
- **Windows, MSVC ABI** (`x86_64-pc-windows-msvc`): the default for Windows
  hosts, as both exec and target platform (`//platforms:win_msvc`): rules_rs
  only ships an MSVC `rustc` for Windows, which can only load proc macros
  built for MSVC. Builds and links against the Microsoft VC runtime and
  Windows SDK, which the llvm module downloads only after their licenses are
  accepted (`BAZEL_MSVC_RUNTIME_VISUAL_STUDIO_EULA`,
  `BAZEL_WINDOWS_SDK_EULA`): put the two `--repo_env` lines from `.bazelrc`
  in a git-ignored `user.bazelrc`. Verified with the patches above:
  `bazelisk build -c opt //crates/ninja-rs` produces an MSVC-ABI
  `ninja-rs.exe` (imports `VCRUNTIME140.dll` and the UCRT) and
  `bazelisk test //...` passes on Windows 11.
- **Windows GNU ABI (gnullvm), cross-built from Linux**: `bazelisk build
  --config=linux --config=cross_windows_gnullvm //crates/ninja-rs` produces a
  PE32+ `ninja-rs.exe` (MinGW-w64 CRT built from source by the llvm module,
  no Microsoft downloads). It runs on Windows and built the sample CMake
  project there. A gnullvm *host* build is not possible (no gnullvm rustc
  exec toolchain in rules_rs).

## mt.exe

The earlier "lld-link: unable to find mt.exe" came from C/C++ executables
linked with `/MANIFEST:EMBED` through CMake. Rust binaries built by rules_rs
don't request manifest embedding, and the Windows MSVC Bazel build links
without `mt.exe`.

## WSL notes

Running Bazel from WSL on the Windows checkout works; pass
`--symlink_prefix=bazel-linux-` so the convenience symlinks don't clash with
Windows ones (they point into the WSL output base). Wrapper scripts are
easier than inline `wsl.exe -- bash -c '...'` (Git Bash rewrites `/mnt/...`
arguments; use `MSYS_NO_PATHCONV=1`).
